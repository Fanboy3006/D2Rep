# ② 数据分析 / 收集层（DATA_ANALYSIS）

> **一句话**：把逻辑层提出的问题，用代码跑成可交付的统计结果。

## 边界（只做这个）
- 解析 replay（Rust `dota_parse`（source2-demo）→ SQLite）
- 数据提取/聚合（英雄走位、购买、眼位、塔、经济、胜负、选手/队伍）
- 统计脚本与可视化（热图、表格、图表、HTML viewer）
- 数据字典（字段含义、口径）

**明确不做的**：
- 不决定"什么值得问"（那是逻辑层）。
- 不修地图/标定坐标（那是地图层）。

## 依赖与方向
- **上游输入**：`06_QUESTION_BANK.md` 的问题清单。每条应写明：要什么数据、口径、输出格式。
- **下游输出**：统计表格 / 数 / 图 + 对应 match id 与取数脚本。

## 交付规范（每条问题交付时）
1. **数据口径**：如何算是/不算（如"10 分钟经济"如何定义）。
2. **样本范围**：哪些场次（970 场？按队/联赛/时间窗过滤）。
3. **可复现性**：脚本名（如 `opendota_analysis/…py`）或 SQL。
4. **缺数据/口径不成立**：回传逻辑层标记"不可统计 / 需重定义"。

## 交接协议
- 用 `05_HANDOFF.md` 模板承接逻辑层的问题；完成后再用同一模板回传结果 + 口径说明。
- 若某问题缺数据没法统计 → 明确告知逻辑层，不硬造结果。

## 已知产物（`analysis/`）
- `run_analysis.py`、`ward_analysis.py`
- `output/`、`output_public/`：逐场 + pooled heatmap CSV、购买统计 CSV 等。
