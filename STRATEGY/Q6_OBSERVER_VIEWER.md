## 0. 一句话

把 **970 场职业赛**里每一支**假眼（Observer）**的插入位置铺到地图上，按**【战队】**与**时间窗**分别统计"这支队伍在这个位置插眼，平均能活多久 / 会不会被反"，并叠一个**【刁钻眼位】**开关（近处有敌方真眼却没被反）。

- 核心开关 = **刁钻眼位**（存活 > 1 分钟 且 存活期间 1200 单位内存在敌方真眼）。

## 2. 指标定义（逐格 × 战队 × 时间窗）

| 指标 | 内部名 | 含义 |
|---|---|---|
| **平均存活**（默认热力） | `avg_surv` | 该格·该队·该窗：假眼**平均存活秒数**（上限 360；未被反且被比赛结束截断的眼按"结束−放置"计，见下方 ⚠2） |
| 假眼出现次数 | `n_obs` | 该格·该队·该窗的假眼**支数**（原始计数，受该战队场次多寡影响） |
| **每场出现次数**（频率） | `per_match` | 支数 ÷ **当前筛选下去重场次数** —— 跨战队/跨窗口可比的**真·频率** |
| **出现率**（频率） | `use_rate` | 该格**至少有 1 支假眼的场次数** ÷ 当前筛选下去重场次数 —— 即"这个点位被使用的概率" |
| 出场场次 | `n_match` | 该格涉及多少场比赛 |
| 被反率 | `dew_rate` | 被反数 ÷ 总数 ×100% |
| **刁钻率** | `tricky_rate` | 刁钻数 ÷ 总数 ×100% |
| 刁钻数 | `n_tricky` | 刁钻假眼支数 |

> **为什么必须有归一化频率**：原始支数会被"该战队打了多少场"淹没（有的队 200 场、有的 10 场）；
> `每场出现次数` / `出现率` 用**当前筛选下的场次数**当分母（分母显示在描述栏，如"分母场次 970"），
> 换战队/时间窗时分母自动跟着变，所以跨维度可比。
> 实测最热两格：格(42,24) **每场 1.21 次 / 出现率 62.2%**，格(76,54) **1.14 次 / 59.5%** —— 即六成比赛都会在这些点位插眼。
>
> **色标（频率热图的关键）**：计数类指标（`n_obs`/`n_match`/`n_tricky`）是长尾分布（实测 p95=31 而最大 1,174），
> 若上限取 95 分位会有 **5.2% 的格被压成同一色**（热点糊成一片红）。现改为：
> ① 计数类指标的**自动上限取 99 分位**（压顶降到 1%）；② 计数类用**对数色标**（`t = log(1+v)/log(1+上限)`，低端被拉开，
> 描述栏标"对数色标"）；率/均值类仍用线性色标。手动拖动"值热力上限"滑块时以你设的值为准。

**刁钻眼位定义（owner 终版，2026-09）**：
> 假眼 **存活 > 1 分钟** 且 **其存活期间 1200 单位内存在敌方真眼**（真视 1050，用 1200 作缓冲）
> **且与该真眼的最长共存 ≥ 60 秒**（第三项为 owner 看了共存分布后追加）。
> 精髓：把"刁钻（近处有真眼却没被反）"与"本来就安全（附近没敌人）"、以及"真眼刚好在插眼那刻到期"区分开。

实现：对每支假眼，遍历同场**敌方**真眼，若 `距离 ≤ 1200` 且两者**最长共存 ≥ 60s**，则记为刁钻；同时记录
`n_enemy_sentry`（**满足同一门槛**的敌真眼支数）、`min_enemy_sentry_dist`（其中最近距离）、**`max_enemy_sentry_overlap_sec`（最长共存秒数）**。
> 判定一律用**导出值**(存活保留 0.1s、共存保留 0.1s):`存活 > 60.0 且 共存 ≥ 下限(默认 60.0)` —— 保证 stdout/JSON/CSV/viewer 四处
> 完全一致, 且"存活 == 销毁−放置"在明细里恒成立(不会出现"存活 60.0s 却标刁钻"这种自相矛盾行)。

> ⚠1 **共存下限已裁定并落地**：早先口径只要求"窗口有交集(>0)"，实测有 **31.3%** 的"刁钻"与敌方真眼共存 < 5s
> （典型是敌方真眼恰好在假眼插下那一刻到期，例：`8765781391` 假眼 11:29.53 插、敌方真眼 11:32.37 到期，相距 1.9 单位只共存 2.84s）。
> **现默认 `--tricky-min-overlap 60`**（≥60s）；`--tricky-min-overlap 0` 可退回旧口径做对照。
> 仍待裁定的只剩**距离上限**：约 15% 的刁钻最近敌真眼落在 **1050–1200**（真视半径之外，只是 1200 缓冲带内）。
>
> ⚠2 **存活被比赛结束截断（右删失，已修，重要）**：比赛在**远古被摧毁**那一刻结束，但战斗日志此后仍继续记录
> **360~925s（中位 398s）的结算残留**（含 354 条守卫死亡 / 30 场）。旧实现把 `MAX(t_cle)` 当比赛结束 → 只标出 2.29%；
> 换成权威结束后，**约 9.5% 的假眼**"放置+360s"其实晚于比赛结束 —— 它们的存活现按 **结束−放置** 计并标 `cens=1`。
> 这直接影响 20+ 窗口的"平均存活"（原先被高估）。复核细节见 `analysis/Q5_RULES_CALIBRATION_LOG.md §19` 与
> `STRATEGY/DEM_FORMAT.md §C6.10`；页面提供 **剔除截断眼** 勾选框供 owner 两种口径对照。

## 4. 口径继承（一条都不改，见 Q5B §4 与 §C6.9）

① 判型靠**实体类名**（`TrueSight`=真眼 / 无后缀=假眼），❌ 不用 combat `inflictor`；
② 放置时刻 = use 的 `t_cle`，**候选窗口 `[实体首见−35s, 首见+2.5s]`**，❌ 禁用 `ward_placed.t_cle`（恒早 540.26s）；
③ **到期 ⇔ `attacker == target`**，其余（敌方英雄/小兵/塔/中立野怪/**同队英雄自毁**）算被反；
④ **寿命是「游戏时钟 cle」常量**（420/360），到期眼的销毁 = 放置 + 寿命；
⑤ **销毁与眼全局一一对应**（代价 = `|Death.tick − (实体末现−9s)|`），❌ 禁"寿命窗内最早"、❌ 不给 use 设独占；
⑥ 死亡只认**权威单位名** `npc_dota_observer_wards` / `npc_dota_sentry_wards`（`LIKE '%ward%'` 会混入瘟疫守卫等，占 8.43%）。

**地图交互**（与 Q5B 一致）：滚轮缩放（以光标为中心，**最小视野半格 86 单位**、超出全图即复位）·
**拖动平移：按住鼠标中键 / 右键 / Shift+左键**（全图下拖动会先放大到 4 格视野再接着平移）·
**点格**＝切到该格并按**当前视野放大 4 倍**（**点已选中的格不再继续放大**；继续放大用滚轮，回全图用 **`复位视野`**）并钻取该格 ·
hover 显示该格数值气泡（含"出场 N 场 / 出现率 / 其中截断 N"）。
**眼点图标**：选中格后，**放大到 ≤8 格（1376 单位）**时该格的眼用**官方假眼图标**（`npc_dota_ward_base.png`，base64 内嵌，与 Q5B 同款）绘制，尺寸 **28px**；只看视野（未选格）时 16px；过密（>900）自动缩到 ~10px 并在描述栏注明。颜色编码画在**图标外圈**：<b>橙=刁钻</b> / <b>蓝=普通</b> / <b>红=被反</b>，锁定的眼再加白圈。图标未加载时兜底画实心点。
**点眼锁定（任务书 §6）**：**点某格后**，点该格内的**眼点**（命中半径 10px）→ 锁定并在图下方显示该眼 `match_id · 双方队名 · 坐标 · 格 · 时间窗 · 放置/销毁/存活 · 被反/截断/到期 · 刁钻 · 期间敌方真眼(数/最近距离/最长共存)`，地图上该点画白圈；再点同一支眼解锁。
> 为什么要求"先点格"：眼点在放大后很密，若任何位置点都可能命中眼点，就会把**点格钻取**这个主操作抢掉（回归测试实测到的冲突）。
> 另一条同样效果的入口：**点右侧明细表的任一行** → 锁定该眼（地图同步画白圈）。
**钻取表**（右侧，跟随当前战队/时间窗/刁钻/截断筛选）：
`match_id ｜ 战队 ｜ 阵营 ｜ 放置 ｜ 销毁 ｜ 存活 ｜ 被反 / 存活状态 ｜ 刁钻? ｜ 期间敌方真眼(达标/任意) ｜ 最近距离(达标/任意) ｜ 最长共存(任意交集)`，时间均为**游戏时钟 mm:ss**；
状态列取值：`到期` / `存活到比赛结束(截断)` / `是被反` / `被反·记录在赛后`。**达标** = 共存 ≥60s（与刁钻同一门槛），**任意** = 半径内窗口有交集。
**点标注**：放大后地图上会画当前视野内的假眼点（<b>橙=刁钻</b>、蓝=普通；<b>红圈=被反</b>）；点格后该格实例全部画出。

> 交互回归测试：`node analysis/q6_viewer_itest.js`（54 项断言；数据自洽 + 表头/明细列数一致 + 缩放/平移/点格/点眼锁定 + 战队多选 + 6 个指标 + 时间窗 4 档）。

```powershell
python analysis\q6_observer.py     # 全量 970 场，约 15 分钟
python analysis\build_q6_html.py   # 约 1 分钟，出 ~4MB 单文件

Copy-Item analysis\output_review\q6_ward_viewer.html publish_repo\q6_ward_viewer.html -Force
```

- 公网：`https://bigfatblackwhale.github.io/DSH-Dota2/q6_ward_viewer.html`（带 `?v=13` 可绕开浏览器缓存）
- **页面顶部有构建戳记**（`构建 2026-09-11 16:15 · 功能版本 v13`）—— 这是判断"你打开的是哪一版"的唯一可靠依据。
  GitHub Pages 发 `cache-control: max-age=600`，**普通刷新（F5）可能仍用缓存**；看不到新功能时先 **Ctrl+F5**，或加上 `?v=13`。
- **部署后校验（本机可跑，直接抓公网比对）**：`node analysis/q6_public_check.js [--wait 180]`
  —— 比对①页面戳记 ②新功能标记 ③内嵌 38,813 条实例是否与源 JSON 逐行相同 ④换行归一后的 sha256。
  实测输出：`公网戳记 == 本地戳记`、`换行归一后 sha256 相同: true`、`内嵌实例 38813 == 源 JSON`。
  （仓库是 LF、本地工作区是 CRLF，所以直接比字节会差几百字节，归一后才是同一份。）
- 改名说明：产物原叫 `q6_observer_viewer.html`，按 owner 要求改为 **`q6_ward_viewer.html`**；旧 URL 留一个跳转页（`<meta refresh>`）指向新页，避免已分享的链接 404 或停在旧数字。
- push 时 `sh.exe: ... Win32 error 5` 是**无害告警**，以末行 `xxx..yyy main -> main` 为准；用 `git ls-remote origin main` 校验落地。
- ⚠ 本机受限环境 **Chrome 起不来**（crashpad 自杀）、TLS 不可用 → 无法自动截图/抓公网页；改用 **Node + DOM/Canvas 桩**做功能级验证（见 §9）。

### 口径开关（owner 裁定项；裁定后一条命令重算）

| 开关 | 默认 | 说明 |
|---|---|---|
| `--tricky-min-overlap S` | **`60`** | 与敌方真眼的**最长共存**下限（秒）。**owner 已裁定 ≥60s**；`0` = 退回旧口径（只要窗口有交集）做对照 |
| `--tricky-radius R` | `1200` | 与敌方真眼的距离上限；可改 `1050`（真视半径本身）—— **这一项仍待裁定** |
| `--tricky-min-surv S` | `60` | 存活下限（秒） |
| `--censor-at-end` / `--no-censor-at-end` | **开** | 右删失：存活窗口被【比赛结束=远古被摧毁】截断（`存活 = 结束−放置`，标 `cens=1`） |
| `--sample N` / `--out DIR` | — | 抽样场次 / 输出目录 |

- 裁定后跑：`python analysis\q6_observer.py --tricky-radius 1050` → 再 `build_q6_html.py` → 重推。
- ⚠ `--censor-at-end` 的**默认值已由"关"改为"开"**（旧默认基于错误的结束时刻，见 §2 ⚠2 / 校准日志 §19）；
  想复现旧数字用 `--no-censor-at-end`（那是"存活=寿命"的**上界**口径）。

| 7 | `surv` | 存活（秒）= `round(destroy−place, 1)`；到期且未被截断 = 360.0 |
| 8 | `dew` | 1=被反 / 0=未被反（到期或截断） |
| 9 | `tricky` | 1=刁钻 / 0=否（按导出值判定：`surv > 60` 且 `ovl > 下限` 且 `n_es > 0`） |
| 10 | `n_es` | **达标**口径：存活期间 1200 内、与敌真眼**共存 ≥ 下限(60s)** 的支数 |
| 11 | `d_min` | 达标真眼中的最近距离（-1=无） |
| 12 | `ovl` | 达标真眼中的**最长共存秒数**（刁钻判据用的就是它：`ovl ≥ 60`） |
| 13 | `cens` | 1=存活被**比赛结束（远古被摧毁）**截断（`destroy = 结束时刻`，`surv = 结束−place`） |
| 14 | `n_es_any` | **任意交集**口径：半径 1200 内、窗口**只要有交集(>0)** 的敌真眼支数（哪怕只共存 1 秒） |
| 15 | `d_min_any` | 任意交集真眼中的最近距离（-1=无） |
| 16 | `ovl_any` | 任意交集真眼中的**最长共存秒数**（明细页"最长共存"列显示的就是它） |

> **为什么要两套口径**：按门槛统计时，一支"只共存 30 秒"的敌真眼会被算成 0 支，看明细的人容易以为数据漏了；
> 所以另出 `*_any` 三列。两者关系恒有 `n_es ≤ n_es_any`、`ovl ≤ ovl_any`、`d_min_any ≤ d_min`（校验器 B10 断言）。
> **刁钻判据仍只用达标口径**：`tricky ⟺ surv > 60.0 且 n_es > 0 且 ovl ≥ 60.0`。
>
> 导出分辨率约定：`place/destroy/surv/ovl/ovl_any` 全部保留 **0.1s**，且 `surv = round(destroy−place, 1)`、`win = f(place)`、
> `tricky` 也按导出值判定 → 四处（分析器 stdout / JSON / CSV / viewer 单文件）**完全可复现**，校验器无需任何豁免。

7b. **底图不跟随视野（已修，`6c10c59`，owner 实测发现）**：底图一直用 `drawImage(bgimg,0,0,CSX,CSX)` 画**整张全图**，而热力块/眼点走的是视野变换 → 一放大，底图与数据就错位（**底图看着没跟着走**）。修法与 Q5B 一致：放大/平移时改为 **9 参 `drawImage` 源裁剪**，把"视野对应的世界矩形→图像像素矩形"铺满画布。
    > 回归测试为什么没抓到：桩里的 `drawImage` **丢掉了参数**、且 `bgReady` 恒为 `false`（Image.onload 不触发）→ 底图分支根本没执行。现已把 ctx 桩改成**记录参数**、并加 `forceBg()` 强制打开底图，断言"裁剪宽高/左上角 == 视野的世界矩形"（全图 5 参、放大 9 参、平移后裁剪原点跟着动、极限放大 86 单位时裁剪 ≈ 4.22px）。
7c. **点格一次性放到"一格铺满屏"（已修，`c363486`，owner 实测反馈）**：点格原先把视野直接设成那一格（172 单位 = 100×），周边全看不见。改为 **`CLICK_ZOOM=4`**：以该格为中心按当前视野**放大 4 倍**（最小半格），连续点不同格会继续 4 倍放大，点同一格复位。回归测试断言 `12040 → 3010 → 753` 且视野中心 == 该格中心。
7d. **眼点是小圆圈、不是官方图标（已修，`c363486`）**：`drawDots()` 一直在画 `arc`（半径 3.5/4.5px = 直径 7~9px），而页面里**早就内嵌了官方假眼图标 base64**（1,922 字节）却没被用。现改为 `ctx.drawImage(obsIcon, …)`，选中格 **28px**（与 Q5B 同尺寸）、看视野时 16px、过密自动缩；颜色编码移到图标外圈。回归测试断言"每个眼点都用官方图标画一次、尺寸 ≥20px、只画选中格里的眼点"。
7e. **图加载完不自动重绘（已修，`c363486`，顺带发现）**：`bgimg.onload` 里调的是**不存在的 `draw()`**（渲染函数叫 `render`）→ 真实浏览器里图加载完成时该回调抛 `ReferenceError`，底图要等下次交互才出现。回归测试新增"onload 回调不抛异常 + 加载完成后 `bgReady=true`"（Node 桩改为**异步**触发 onload，与浏览器一致）。
7j. **布局 v17（`7250db1`，owner 实测：地图超出分辨率、与明细表对不齐）**：
    - **地图不再超出屏幕**：画布是正方形，之前用 `width:100%` + `flex-grow` 会被拉到比窗口还宽，等比放大后高度溢出（owner：「地图太大了，超过了分辨率的范围」）。
      现在 `canvas{width:min(100%, max(320px, calc(100vh - 430px))); aspect-ratio:1/1}` —— **边长 = min(该栏宽度, 视口高 − 固定占用)**，且恒为 1:1（不会被拉扁）。
    - **两栏顶部对齐**：控件（战队多选 / 阵营 / 时间窗 / 指标 / 三个滑块 / 复位视野）原来是放在**左栏地图上方**的，所以右栏的明细表从最顶开始、与地图顶部差着整个控件块的高度。
      现在控件抽成**整行的 `.controls` 块放在两栏之上**，地图与明细表在同一行、顶部对齐。
    - 右栏宽度改 `clamp(360px, 34vw, 660px)`（大屏给得宽、小屏不至于挤到没法看）。
    - **回归测试加了 7 条"布局契约"断言**（本机无法渲染 CSS，于是把布局规则本身钉住）：两栏 `flex-wrap:nowrap`、画布边长用 `min(100%, …100vh…)`、`aspect-ratio:1/1`、右栏 `clamp(...)`、控件块在 `.wrap` 之前、画布在 `.wrap` 内、控件元素移出后仍在（`curdesc/orgstat/ns`）。

7i. **v16 四条（`5db7400`，owner 实测）**：
    - **拖动不再带着缩放**：很多鼠标**按住滚轮(中键)时设备还在发 `wheel` 事件**，原来那些事件会把拖动顺带变成缩放（owner：「中键按下去还带着缩放，拖动效果很差」）。
      现在滚轮处理里先判 **`dragging || (e.buttons & 6)`**（中键/右键**正被按住**就完全不吃滚轮）—— 用位掩码而不是"拖动后 N 毫秒忽略"，没有时间魔法、也确定可测。
    - **4× 档就能看到假眼的准确位置**：眼点图标不再只在 ≤8 格时才画 —— **有选中格时，4 倍档(4300)及以内都画**；尺寸按缩放档**阶梯**：`4 倍档 12px → ≤8 格 20px → ≤2 格 28px`（4 倍档格子只有 ~41px，12px 才看得出"位置"）；画序把普通眼放在下面、刁钻/被反压在上面。
    - **明细表覆盖"中心格 + 周围 8 格"**：新增 **「格」列**（`C`=你点的中心格、`N`=周围 8 格，含格号），排序中心格优先、其余按格距+放置时刻；汇总行写"及周围 8 格（中心格 N 支）"；3×3 在大格上可能上千行 → 加 **4000 行上限** 并明确提示"共 N 行，只列出前 4000 行，请缩小筛选范围"。
    - **布局改成"明细表永远在地图右侧"**：`.wrap` 去掉换行（`flex-wrap:nowrap`），`canvas{width:100%;height:auto}` —— **窗口不够宽时按比例缩小地图**，而不是把明细表挤到下面（画布点击换算本来就用 `getBoundingClientRect()`，缩放后命中依旧正确）。
7h. **点格只剩两档（v15，`76f5c02`，owner 口径终版）**：owner 明确「通过点击方块格进行的放大**就只有 4x 和非 4x 这两个档位**，剩下的让用户用滚轮缩放」。现在的规则（都有断言）：
    - 点任意格 → 把视野切到 **4 倍档（全图/4 = 4300 单位）并以该格为中心**；
    - **点别的格** → 仍是 4 倍档，**只重新居中**（不在当前基础上叠乘 4 倍）；
    - **点已选中的格** → 视野不动；
    - **已用滚轮缩到 4 倍以内**时点格 → **保持滚轮那个档位**，只居中（不会被拉回 4 倍，也不会继续放大）；

7g. **UI 交互第二轮（`b59f972` / `84dd124`，v14，owner 实测）**：
